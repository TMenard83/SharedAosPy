# tournament_kit — PDF de tournoi (liste + cartes maison)

Lire avant de modifier ce paquet (CLAUDE.md ne garde que la carte des couches).

**`tournament_kit/`** (needs `[roster]`: reportlab + pypdf) — self-contained, no DB access. Compiles a raw army-list export + its battletome unit profiles into one tournament-ready PDF. See "Tournament kit" below.

## Carte des modules

Ordre des dépendances, du bas vers le haut :

- `sources/` — chargeurs (aucune décision de mise en page) : `wahapedia_lookup` (CSV Wahapedia, EN), `warscroll_index` (index des pages de PDF), `tactic_cards`, `faction_rules_fr` (verbatim FR / textes de l'app EN), `generic_core_abilities`, `season_rules`, `roster_simplifications`.
- `modes.py` — `RosterMode` (nom CLI) → `ModeSpec` gelé (`french`, `curated_patch`, `french_names`, `page_copy`, `extended`, `split`, `simple`, `english`, `file_label`) ; remplace les anciens tuples `FR_MODES`/`SPLIT_MODES`/….
- `render/` — rendu reportlab des cartes : `options` (`RenderOptions` gelé + `RenderTracker`, portés par un `ContextVar` : `render_session()` par PDF, `update_render_options`, `render_options_override` le temps d'un bloc), `theme` (police, couleurs, styles), `text` (`clean_html`, flavor, gras « Placer », `tr()`/libellés EN, capacités d'arme FR), `phases` (`classify_phase`, catégories, côtés du tour, sections), `pills` (pastilles, `_CastBadge`, légendes), `layout` (rail de phase, bandeaux, `_chunk_group`, colonnes, bandeaux sectionnés, deux colonnes de cartes), `cards` (`render_warscroll_card`/`render_rule_card`/`render_tactic_card`).
- `resolution/` — quel texte retenir : `rules_resolution` (`resolve_rules`), `absent_references`.
- `split_pool.py` (pool d'aptitudes étendu/split : clusters de choix, alias, ordre du déploiement, retraits), `assembly.py` (PDF de chaque section, pypdf, scénarios, numéros de page), `cover.py` (couverture).
- `pdf_builder.py` — orchestration (`build_roster_pdf`, `default_output_path`, `RosterPdfResult`).
- `warscroll_card.py` — façade de transition qui réexporte `render/*` (privés compris) ; le nouveau code importe directement depuis `render/`.

Les sections ci-dessous gardent leur rédaction d'origine ; un nom `render/<module>.<nom>` ou `<module>.<nom>` y désigne son emplacement actuel.

## Tournament kit (`tournament_kit/`) — roster + unit-profile PDF, no DB, no rasterization

`aospy roster pdf --list <fichier>` (needs `[roster]`) compiles a raw army-list export (`data/Proposition de listes/*.txt`, the plain-text format Warhammer Age of Sigmar: The App produces) into one PDF, in this order (non-split modes: the warscroll cards come right after the cover instead, see "Roster modes"): a formatted cover of the list, **one merged "maison" rule card** — Battle Traits + chosen Formation + Heroic Traits + Artefacts of Power + chosen Spell Lore + chosen Manifestation Lore, all pooled together and sorted by phase band rather than one card per category (`resolution/rules_resolution.resolve_rules`; falls back to a French battletome page *per category* for whatever Wahapedia doesn't cover) — the cited battle tactic cards (also "maison", verbatim French, `tactic_cards.py`), each listed unit's **"maison" warscroll card** (English, reportlab-drawn, not a copied page) plus the full warscroll of every manifestation the chosen lore can summon, and, only if something isn't covered by Wahapedia nor any battletome/Manuel du général PDF, an English appendix (see "Wahapedia fallback" below). A manifestation lore always pulls in **every manifestation it can summon**, not just its casting-rule ability — choosing the lore gives access to all of them at the table, so resolving just the "convocation" text (and not each manifestation's own warscroll) is a bug, not a size optimization; worth re-checking whenever `warscroll_index.json` is extended to a new battletome. No DB access; entirely driven by hand-curated data files plus the already-downloaded `data/wahapedia/*.csv`.

- **`tournament_kit/render/`** (ex-`warscroll_card.py`): draws a unit's profile (`render_warscroll_card`), a faction rule card (`render_rule_card` — no stat bar or weapons, abilities from every category already pooled and tagged with an origin badge by the caller, see above), or a battle tactic card (`render_tactic_card`, see below) as a compact reportlab `Table` flowable. Abilities are grouped under a **vertical phase rail** (`_PhaseRail`, a `Flowable` subclass that paints a filled rect and rotates the phase label 90° via `canvas.rotate()` — its height is measured from the group's own body table *before* the rail is built, `_ability_group_body(...).wrap(...)`, which is how a `Flowable` whose height reportlab only knows after layout gets a rotated label anyway; `_min_rail_height` floors it at the rotated label's own measured string width so a very short group can't clip it) — 7 phases from `data/Manuel du général/MdG26-27 Aptitudes.pdf` (pixel-sampled), plus an 8th green "any phase" band for reactions the CSV's `ability_phase = "Defensive reaction"` doesn't tie to one specific phase (reclassified from the ability text: mentions `Fight ability`/`combat attack` → Mêlée, `shooting attack` → Tir, otherwise → the green band; shared by every renderer via `_append_ability_groups`). A single phase group that would be taller than one page (only possible once rule-card merging pools several categories into the same phase) is split by `_chunk_group` into several same-labelled rail segments rather than overflowing. Badges (frequency, qualifier — `Your`/`Any`/`Enemy` → *Ma phase*/*Les 2 phases*/*Phase ennemi* — passive, reaction, ability keyword, weapon range/wielder-ratio, and on a rule card an extra "origin" badge folded into `keywords` via `tag_ability_origin`) are **true filled pills** (`_pill` — a small single-cell `Table` with a `BACKGROUND`/`BOX` style, since `Paragraph` alone never paints a background behind flowing text) rather than bracketed colored text — matches the original HTML design mockup (a "horizontal band + bracketed text" layout is a regression the user rejected). `build_warscroll_cards_flow`/`pack_cards_two_columns` stack warscroll cards in two independent columns per page (each card, in list order, goes to the shorter column where it fits; a card that no longer fits moves to the next page while later cards that still fit backfill the current one), and keep every manifestation warscroll together on one page (`groups`) — general rule, every mode; rule cards and tactic cards are *not* paired this way (`_build_rule_cards_pdf`/`_build_tactic_cards_pdf`, `pdf_builder.py`) since their length varies too much for a `KeepTogether`'d pair to make sense — each is just stacked, with a tactic card individually wrapped in `KeepTogether` so two short tactic cards still land on the same page without splitting either one across it. Unit profiles are never page-copied — `pdf_builder.py` reads no unit page from any battletome PDF, only `wh.find_warscroll`; a unit not in Wahapedia at all is a genuine `units_unmatched` entry. For faction rule categories it's Wahapedia-first with a page-copy fallback per category (`rules_resolution._WAHAPEDIA_RULE_CATEGORIES`, `WahapediaLookup.find_faction_category`) — the Battle Formation card is filtered to the one the list actually chose via `ParsedList.allegiance` (misleadingly named: it's literally the chosen Battle Formation's name, e.g. `"Despoilers"`/`"Warhost of Duality (20 Points)"` — confirmed against `Faction_abilities.csv`'s `subtype_name` under `type_name = "Battle Formations"`); Battle Traits/Heroic Traits/Artefacts of Power include every entry the faction has (no per-hero selection parsing yet). A Spell Lore/Manifestation Lore is treated as an ability category like any other (`rules_resolution.resolve_rules`) — Wahapedia-first via `find_faction_category`, then the French page (`find_lore_pages`/`generic_manifestation_lores`), then the English Wahapedia text block, in that order; a manifestation lore only switches to the card path if *every* manifestation it grants resolves via `find_warscroll` (else the whole thing falls back together, never half-card/half-page). Wahapedia's scraped fields carry a few corruption patterns handled by `render/text.clean_html`: a truncated `<a href="...` with no closing `>` (field cut off mid-attribute), stray `%\d+`/`$\d+` single tooltip-id markers wrapping or prefixing real inline text (stripped, including a leftover `$id|` separator), and a **run of 2+ such ids glued back-to-back with nothing between them**, which is not decorative noise but a reference to content (e.g. LRL's "Depict Rune", 5 runes' individual effects) that Wahapedia resolves client-side from a tooltip table absent from all 13 downloaded CSVs: a genuine, unrecoverable data gap, not a parsing bug, so it's replaced with a visible `[texte manquant dans l'export Wahapedia — voir le Manuel du général/l'App]` note instead of silently vanishing.
- **`data/json/battle_tactic_cards.json`** / **`tournament_kit/sources/tactic_cards.py`**: the 6 Battle Tactic Cards for the 2026-27 season, hand-transcribed **verbatim in French** (same "no text layer, PyMuPDF-render-then-read" procedure as `warscroll_index.json`, applied to `MdG26-27 Tactiques.pdf`'s 6 pages) — same hand-curated-JSON convention as `army_rules.json`/`warscroll_index.json`, loaded fresh (`load_tactic_cards`, no DB). Unlike unit profiles/faction rules (Wahapedia, English, with a French-page fallback), tactic cards stay French and have no fallback at all: they exist in no other source. `render_tactic_card` (`warscroll_card.py`) draws each card's optional "règle spéciale" (a pre-battle setup rule 2 of the 6 cards carry) and its 3 sub-tactics (Échauffourée/Frappe/Domination, one colored pill each — reusing the same badge-severity palette as ability badges, not a new one) plus a dedicated, larger "points de victoire" pill (`_points_badge`) per sub-tactic. No page copying — `assembly._build_tactic_cards_pdf` stacks the cited cards' `Flowable`s compactly enough that the common 2-cards-per-list case lands on a single page.
- **Rules only, no flavor text** (every mode): `render/text.strip_flavor` drops a description's leading `<i>…</i><br/>…` block at render time (the form of every battletome-transcribed French description in `faction_rules_fr.json`; Wahapedia keeps its flavor in `AbilityEntry.legend`, never rendered), and `render_tactic_card` no longer draws `card.flavor`/`sub.flavor`. The JSON files keep the full verbatim — only rendering skips it.
- **Battle tactic cards always share one page**: `assembly._tactic_cards_block` wraps all cited cards in a single `KeepTogether` (both in the standalone tactic section and inside `fr-split`'s "Mon tour" flow).
- **Generic abilities tied to a unit keyword**: a `generic_core_abilities.json` row can carry `requires_unit_keyword` ("MUSICIAN" for "Musicien", "STANDARD BEARER" for "Porte-Étendard", "CHAMPION" for "Champion" — a `(…)` suffix on the unit keyword is ignored); `load_generic_core_abilities(..., unit_keywords=...)` drops it unless some unit of the list carries that Wahapedia keyword.
- Card-sheet PDFs (rule/tactic/warscroll cards) use a narrower page margin than the cover/appendix (`assembly._CARD_PAGE_MARGIN`, 5.5mm vs. 18mm) — deliberately thin, to leave more of the page to the cards themselves.

- **`tournament_kit/list_parser.py`**: line-based parser for the App's stable export format (title, faction, optional allegiance, `Drops:`/lore/`Battle Tactic Cards:` header, `General's Regiment`/`Regiment N` sections of `Name (points)` lines with ` • Option` sub-lines attached to the preceding unit, an optional `Regiments of Renown` section — `Name (total points)` followed by its member unit names with no points of their own, since already included in the total — and an optional `Faction Terrain` section) → `ParsedList` dataclass. `ParsedList.base_faction` strips an Army-of-Renown suffix (`"Slaves to Darkness | Legion of the First Prince"` → `"Slaves to Darkness"`) since the base battletome is what's indexed under that name; `unique_unit_names()` folds in Regiment of Renown member units too (the regiment itself has no unit profile — see below).
- **Why the source PDFs need their own hand-built index rather than a text search**: GW's PDF battletomes (`data/Battle tome/Done/*.pdf` — `DEFAULT_BATTLETOME_DIR`; `Battle tome/A curer/` holds battletomes not yet curated into `warscroll_index.json`/`faction_rules_fr.json`, `Battle tome/Draft/` holds not-yet-adopted extras, and `Battle tome/Download GW/` holds raw downloads not yet sorted into either — all three out of scope for the index/lookup code) **and** the Manuel du général core-rules PDFs (`data/Manuel du général/*.pdf`) carry **no text layer at all** (aplatis/vectorized anti-copy treatment) — confirmed page-by-page with PyMuPDF before building anything, on both directories. `data/json/warscroll_index.json` is therefore curated by hand — page-render-and-look, cross-checked against the DB's already-imported canonical unit names (`unit.name`/BSData spelling, which matches the App export's unit-name spelling) for units, and against the exact English wording of a list's `Spell Lore -`/`Manifestation Lore -`/`Battle Tactic Cards:` fields for rules/cards — the exact same "hand-curated JSON, extended incrementally" convention as `data/json/army_rules.json` (CLAUDE.md, "Data files"). See the `warscroll-index` skill (`.claude/skills/warscroll-index/SKILL.md`) for the full curation procedure.
- **`data/json/warscroll_index.json` shape**: top-level `"factions"` (keyed by faction name) each with `"file"`, `"units"` (name → pages, each entry optionally carrying its own `"file"` override — see below), and `"rules"` — `battle_traits`/`formations`/`heroic_traits_artefacts` (single page list each, always included when present) plus `spell_lores`/`manifestation_lores` (name → pages, since a faction usually offers several and only the one a list actually cites should be pulled in — a manifestation lore's page list must include the casting-rule page *and* every one of its manifestations' own warscroll page(s), not just the former); a faction-independent top-level `"battle_tactic_cards"` (`dir`/`file` pointing at `Manuel du général/MdG26-27 Tactiques.pdf`, one page per named card — kept for provenance/tests, `find_tactic_card_pages`/`tactic_cards_path`, but no longer read by `pdf_builder.py`, which renders tactic cards from `data/json/battle_tactic_cards.json` instead, see above); and a faction-independent top-level `"generic_manifestation_lores"` (`dir`/`file` pointing at `Manuel du général/sorts persistants - manifestations.pdf`, `"lores"` keyed by the lore's English name, each with `"domain_pages"` — the casting-rule page(s) — plus `"manifestations"` — name → warscroll pages, one entry per manifestation that lore can summon).
- **`tournament_kit/sources/warscroll_index.py`**: loads that JSON fresh each call into a `WarscrollIndex(factions, tactic_cards, generic_manifestation_lores)` (no DB, mirrors `bonus_simulator/army_rules.py::load_army_rules`). `find_pages`/`find_tactic_card_pages` match exactly first then fall back to accent/case-insensitive (`_lookup_normalized`); `find_lore_pages`/`find_generic_manifestation_lore` additionally retry with anything from `"("` onward stripped, since a list export sometimes suffixes a lore with its point cost (`"Morbid Conjuration (20 Points)"`) that the index key doesn't carry. `GenericManifestationLore.all_pages()` concatenates `domain_pages` with every manifestation's pages — the caller always wants all of them, since picking the lore gives access to every manifestation in it, not just one. A `FactionIndex` is one battletome PDF per faction by default, but a unit's own entry can override that with its own `"file"` (`UnitEntry.file`, defaulting to the faction's `file` when absent) for a unit whose charte lives in a separate supplement rather than the base battletome — the motivating case is a small "Scourge of Aqshy" PDF covering just the 1-2 units GW released that way instead of folding them into the main book; `unit_pdf_path(index, faction, unit_name, battletome_dir)` resolves the correct PDF per unit, while `battletome_path` stays the one-PDF-per-faction shortcut for whole-faction rendering (cover, rule pages, etc.) and is unaffected by the override. Note that `find_pages`/`unit_pdf_path` aren't currently called by `pdf_builder.py` in production — unit cards are rendered from Wahapedia data (`wh.find_warscroll`, see `warscroll_card.py` below), not by copying a battletome page — so today the `"units"` list is exercised only by `tests/tournament_kit/test_warscroll_index.py`; it's still curated for completeness/provenance and in case a future page-copy path needs it again.
- **`tournament_kit/pdf_builder.py`**: `build_roster_pdf` renders a cover with `reportlab` (portrait `SimpleDocTemplate`, reusing `pdf_theme.py`'s palette — shared with `reports/common.py`, whose own `build_document` is landscape/table-oriented and doesn't fit here), then calls into `resolution/rules_resolution.py::resolve_rules`, which pools every rule category Wahapedia covers into one `render_rule_card` call and resolves the cited battle tactic cards via `tactic_cards.find_tactic_card` — `build_roster_pdf` itself then falls back to `_append_pages`-style page copying (deduplicated per source PDF — one battletome page is often a 2-unit spread) only for whatever category/lore `resolve_rules` reports as uncovered. A manifestation lore not covered by Wahapedia is tried against two more sources in order, each its own dedup'd `PdfReader`: the faction's own battletome (its faction-specific lores), then `generic_manifestation_lores` (the shared/cross-faction lores, French, `Manuel du général/sorts persistants - manifestations.pdf`), then the Wahapedia English text-block fallback below as the last resort. Anything none of these resolve is collected into `RosterPdfResult.units_unmatched`/`rules_unmatched` and printed both on the cover page and by the CLI, never a hard failure, mirroring the importers' `skipped_*` counters.
- **`aospy roster pdf`** (`cli/roster.py::cmd_roster_pdf`) needs no `_connect(args)` — this whole feature is DB-free by design. Missing `[roster]` prints the same "install this extra" message pattern as `cmd_cost_fit`'s `[analysis]` check.
- Companion units that ride along a paid entry for free (e.g. Slaves to Darkness' "Singri Brand"/"The Oathsworn Kin" bundled with "Gunnar Brand") are merged away in the aospy DB (see `importers/README.md`, "Composite/companion unit merging") but still appear as their own named lines in the App's list export — `warscroll_index.json` indexes them under their own name directly (not derivable from the DB), separately from the merge logic.

### Wahapedia fallback (`tournament_kit/sources/wahapedia_lookup.py`) — English appendix for what's in no PDF at all

Regiments of Renown (a different AoS4 concept from the "Army of Renown" supplements above), Army-of-Renown-only units/rules, and generic cross-faction *spell* lores used across the sample lists are absent from `data/Battle tome/` and `data/Manuel du général/` (confirmed by reading every page of both). They *are*, however, already present in English in the Wahapedia CSV export the `wahapedia` importer already downloads (`data/wahapedia/*.csv`, itself text — no curation/page-hunting needed, unlike the PDFs above). The 6 generic cross-faction *manifestation* lores (`Twilit Sorceries`, `Aetherwrought Machineries`, `Krondspine Incarnate`, `Forbidden Power`, `Primal Energy`, `Morbid Conjuration`) are covered by a user-supplied scan (`Manuel du général/sorts persistants - manifestations.pdf`, French, resolved via `generic_manifestation_lores` above, tried before this Wahapedia fallback) — this Wahapedia path stays as the catch-all for anything even that scan doesn't cover:

- Generic lores live under the pseudo-faction `faction_id == "EnS"` (Endless Spells) in `Faction_abilities.csv`, keyed by `subtype_name` (e.g. `"Twilit Sorceries"`) — `find_generic_lore` groups its rows by `line`.
- An Army of Renown's own rules (Battle Traits/Heroic Traits/Artefacts of Power/Spell Lore/Manifestation Lore, all of them) live under its own `type_name` (e.g. `"Legion of the First Prince"`) in the same file, this time distinguished by `subtype_name` as the *category* — `find_renown_army_rules` groups by that. Its member units are stored in `Warscrolls.csv` under their bare name (`"Legion of the First Prince Bloodletters"` in a list export is just `"Bloodletters"` in Wahapedia) — `pdf_builder.py` retries the lookup with the renown-name prefix stripped before giving up. **The categories an Army of Renown carries *replace* the base faction's equivalents** rather than supplementing them (e.g. "Legion of the First Prince" replaces Battle Traits/Heroic Traits/Artefacts of Power/Spell Lore/Manifestation Lore, but not Battle Formations — it has none of its own) — `rules_resolution._AOR_REPLACES` maps each `_STATIC_RULE_SECTIONS` attribute to the `subtype_name`(s) that supersede it, and `resolve_rules` omits the base battletome page for any category the chosen Army of Renown actually replaces, so the PDF never shows both the superseded French page and the replacement English one side by side.
- A Regiment of Renown is its own `Warscrolls.csv` row (`role == "Regiment of Renown"`, no stat line of its own) with composition in `Warscrolls_organisation.csv` and its own bonus ability in `Warscrolls_abilities.csv`, both keyed by that row's `id` — `find_regiment_of_renown` assembles the three. Several near-duplicate rows exist (one per faction allowed to take it); the one with a non-empty `legend` is its faction of origin and is preferred. Its member units (e.g. Skarbrand, native to Blades of Khorne) are then resolved the normal way via `find_warscroll`, which searches *all* factions, not just the list's own. When a Regiment of Renown has exactly one member (e.g. "The Exiled One" = Skarbrand alone) and that member is itself rendered via the Wahapedia English fallback, `assembly._build_wahapedia_appendix_pdf` skips the separate "Regiment of Renown — X" section and folds the regiment's own ability straight into that unit's card instead (`_render_warscroll(..., regiment_note=..., extra_abilities=...)`) — a one-member "regiment" and "the unit" read as the same thing, no need for two structures. A regiment with several members still gets its own section as before.
- `render/text.clean_html` converts Wahapedia's markup (`<a href>` unwrapped, `<span class="kwb...">` → `<b>`, `<ul><li>` → bulleted `<br/>`-separated lines) into what `reportlab.platypus.Paragraph` accepts; `_safe_paragraph` falls back to fully tag-stripped plain text on any parse error, because this CSV snapshot is scraped external data and at least one field is truncated mid-tag (`Faction_abilities.csv`'s `"FIRST-DAMNED PRINCE"` battle trait) — never let one malformed row crash the whole PDF.
- Everything resolved this way is rendered on its own clearly-labelled "ANNEXE — CONTENU WAHAPEDIA (ANGLAIS)" pages appended at the very end of the PDF (never interleaved with the French battletome content) and listed in `RosterPdfResult.wahapedia_used` — a deliberate choice (confirmed with the user) not to machine-translate rules text, to avoid a mistranslation misleading someone about actual game rules.

### Roster modes (`build_roster_pdf(..., mode=...)` / `aospy roster pdf --mode ...`)

Everything described above is the `hybrid` mode (default, unchanged historical behavior). 4 more variants exist, selected by one `mode` argument threaded through `resolve_rules`/`build_roster_pdf` (`RosterMode`, defined in `resolution/rules_resolution.py` and re-exported by `pdf_builder.py`) and gating every per-category resolution the same way:

- **`en`**: Wahapedia only — the French battletome-page-copy fallback tier (`_STATIC_RULE_SECTIONS`, and the French-page tiers of the spell-lore/manifestation-lore chains) is simply skipped (`resolve_rules`'s `allow_page_copy = mode == "hybrid"`); anything Wahapedia doesn't cover shows up as a plain `RosterPdfResult.rules_unmatched`/`units_unmatched` entry, never an interactive prompt — the CLI run itself never blocks waiting on input. (A separate, conversational workflow — comparing Wahapedia's English data against an actual battletome/faction-pack scan and asking for a missing page when a real gap turns up — is a curation/audit concern, not something this mode's plumbing does; out of scope for `pdf_builder.py` itself.)
- **`fr`**: like `en` (no page copy) but every Wahapedia-resolved category also passes through `data/json/faction_rules_fr.json` (`sources/faction_rules_fr.py`, see below) via `rules_resolution._fr_patch`, which corrects/completes the pool wherever a curated French entry exists for that faction/category/unit — a faction with nothing curated yet degrades naturally to the same result as `en`, no special-casing needed.
- **`fr-extended`**: `fr` plus one more rule card, "Aptitudes Génériques — MdG26-27" (`data/json/generic_core_abilities.json` / `tournament_kit/sources/generic_core_abilities.py`, a loader twin of `season_rules.py` for the *complete* `MdG26-27 Aptitudes.pdf` rather than just its page-5 season rules) — omitted entirely (not an empty card) if that file has no entry.
- **`fr-split`**: same *content* as `fr-extended` (`ModeSpec.french` in `modes.py` gates every French-patch check, so a new French mode only needs a `MODES` entry there), different *layout*: every warscroll's abilities leave its unit card (which keeps only stat bar + weapons + keywords) and join the merged rule pool, each tagged via `AbilityEntry.warscrolls` (rendered as a dedicated night-blue pill, `render/pills._warscroll_pills`; an identical ability carried by several units is merged into one entry with one pill per unit, `split_pool._warscroll_ability_pool`). That pool is then split into three rule cards, each starting on its own page: "Déploiement" (every `deploy`-band ability, which precedes any turn, followed by the green "N'importe quelle phase" band, which would otherwise be duplicated on both turn cards), "Mon tour" / "Tour adverse" (by `render/phases.ability_turn_sides` — the same `Your`/`Enemy`/`Any` qualifier regex as the "Ma phase"/"Phase ennemi"/"Les 2 phases" pills; passives, reactions, "Début de round" and unqualified conditions go on *both*). Cards order their bands by `render/phases.SPLIT_PHASE_ORDER` (green band right after deployment, `render_rule_card(..., phase_order=...)`; other modes and unit cards keep `_PHASE_ORDER`), so "Fin de tour" is a turn card's last band; the battle tactic cards are not a separate section in this mode, they follow right after it, inside "Mon tour"'s page flow. "Tour adverse" drops « En Avant, vers la Victoire » (charge reroll command) unless another ability on that card carries the `Charge` keyword (`split_pool._drop_enemy_charge_reroll`) — otherwise the only unit charging there is the Contre-Charge one, which already used its one command. « Au Pas de Course » / « At the Double » (reaction to a Run, only possible in your own movement phase) is always dropped from « Tour adverse » (`split_pool._MINE_ONLY_KEYS`). A reaction limited to « in your … phase » / « dans votre phase » goes on « Mon tour » only (`render/phases._IN_YOUR_PHASE_RE`, e.g. « Avancer dans la Trace »). Turn cards also hide the "Ma phase"/"Phase ennemi" pills (`render_rule_card(..., hide_turn_qualifier=True)`, the card title already says it; "Les 2 phases" stays). Passive abilities that change the unit's own profile with its damage taken (`render/phases.is_profile_modifier`, e.g. "Battle Damaged"/"Stigmates de Guerre", bilingual regex) stay on the warscroll card instead of joining the turn cards. **Choice sub-sections** (`split_pool._CHOICE_CLUSTERS`, one `_ChoiceCluster` per faction, applied by `_apply_choice_clusters`): a titled sub-section opening a phase band with the ability that makes you *choose* followed by every option — FEC "Délires" ("Royaume Délirant" + every `Delusion`-keyword ability, `fr-extended`+`fr-split`), BoK "Dîme de Sang" ("Des Crânes pour le Trône de Crânes", "Trempés de Sang", then every `Blood Tithe` ability by cost, `fr-extended`+`fr-split`, both turn cards), DoK "Bénédictions de Khaine" ("Rites de Sang" then "Bénédictions de Khaine", in the *Fin de tour* band, `fr-extended`+`fr-split`). Any reaction to a choice ability (Wahapedia condition « You declared the ‘<name>’ ability », `_is_choice_reaction`, e.g. Blood Hags' "Offrandes Pourpres") is moved into its sub-section. In `fr-extended` only faction rules are pooled, so warscroll options/reactions stay on their unit card there. An option acting in another phase is deliberately *also* kept there (duplicate); one already in the cluster's phase is moved rather than duplicated. `classify_phase` trusts a cluster copy's `ability_phase` over the phase its `condition` names. A sectioned phase band that misses the space left on its page by 5% or less is laid out again wider then scaled down to the card width to fit there (`render/layout._SHRINK_TO_FIT`, `_SectionedPhaseGroup.rebuild`, `_ShrunkFlowable` — same width as the other bands, text slightly smaller) rather than moved to the next page. A choice sub-section must fit on one page (user request): `render/layout._choice_segments` makes it its own chunk with a taller budget (`_MAX_CHOICE_HEIGHT`, 265mm vs. `_MAX_GROUP_HEIGHT`'s 240mm — the real frame is ~273mm), and its defining keyword pill (`DELUSION`/`BLOOD TITHE`) is hidden inside it, while a warscroll option keeps its unit pill there (the sub-section title doesn't name the unit, `_warscroll_pills`); 3 columns were tried and came out taller. **Rule**: each cost type has its own `_CastBadge` silhouette (`_CAST_BADGE_SHAPES` — circle spell, diamond prayer, hexagon CP, blood drop blood tithe), never shared (`test_cast_badge_shapes_are_unique`). These cards' phase bands are far bigger than any other mode's, which is why `_chunk_group` measures at the real column count and splits an oversized category cluster per ability.

**`data/json/faction_rules_fr.json`** / **`tournament_kit/sources/faction_rules_fr.py`**: hand-curated French verbatim for a faction's rule categories (`battle_traits`/`formations`/`heroic_traits_artefacts`/`spell_lores`/`manifestation_lores`/`prayer_lores`, same names as `_STATIC_RULE_SECTIONS`/`data/json/warscroll_index.json`'s `rules` keys) *and* per-unit ability text (`factions.<name>.units.<unit>.abilities`), transcribed from a battletome ("BT"), a faction pack ("FP", a faction's provisional rules before its battletome ships) or a seasonal supplement like Scourge of Aqshy ("Aqshy") — same hand-curated-JSON convention as `warscroll_index.json`/`army_rules.json`, extended one faction at a time (`faction-rules-fr` skill). A unit entry can also carry display keys: `subtitle_fr` (French name in small grey italics under the English card title — the App exports lists in English, so the English name stays the anchor; `WarscrollData.subtitle`), `weapons` (`wahapedia_name` → French `name`, full French weapon names in FR modes) and `name_fr` (replaces the title — only used for manifestations, which the list export doesn't name). Each JSON entry is either a **patch** of an existing Wahapedia ability (`wahapedia_name` set to Wahapedia's exact English name — the join key `pdf_builder.apply_fr_overrides` matches on; only `name`/`description` are overridden, every other field — `condition`/`ability_phase`/`points_type`/`points` — stays whatever Wahapedia already had, no need to re-transcribe mechanically-derived fields) or a **standalone addition** (no `wahapedia_name`/no match — e.g. genuine Scourge-of-Aqshy content Wahapedia doesn't carry at all — in which case `condition`/`ability_phase` must be hand-filled with the same internal English mini-vocabulary `season_rules.json` already uses, never shown as-is). `formations`/`spell_lores`/`manifestation_lores`/`prayer_lores` entries carry a `scope` field (the formation/lore name) so only the option the list actually chose applies (`get_faction_category_overrides(..., scope=...)`, same `split("(", 1)[0]` normalization as `WahapediaLookup.find_faction_category`'s `subtype_name` filter); `battle_traits`/`heroic_traits_artefacts` have no `scope` (every entry applies, mirroring Wahapedia). A standalone addition is only meaningful for `manifestation_lores` as a *patch* — `resolve_rules` resolves each summonable manifestation's warscroll (`find_warscroll` on the `"SUMMON <name>"` prefix) *before* applying French patches, precisely so a patch can't rename that join key out from under the lookup; a from-scratch manifestation ability would have no warscroll to attach to. Each patched entry also carries a `provenance` object (`bt_text`/`errata_patch`/`errata_source`) recording the original battletome text and, if the ability was touched by a "MISES À JOUR DE RÈGLES" errata page, the correction as printed — kept purely for audit/re-curation, never read by `rules_resolution.py`/`pdf_builder.py` (`description` already holds the final corrected text that gets rendered). `rules_resolution._apply_ability_text_overrides`/`_ABILITY_TEXT_OVERRIDES` (the older, single-entry ad hoc fix for one corrupted Wahapedia field, LRL's "Depict Rune") is unrelated and still applies in *every* mode, unconditionally — it now runs *after* `_fr_patch` specifically so a future `faction_rules_fr.json` entry for that same ability can still match Wahapedia's pristine English name; once such an entry exists, the legacy override simply becomes a no-op for it since the name it looks for is already gone.
