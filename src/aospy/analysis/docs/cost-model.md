# Cost model — scope vs StatHammer

Détail déplacé de `analysis/README.md` (lire seulement avant de toucher ce module).

Ported from StatHammer's own modules, adapted to aospy's already-typed schema (no text parsing needed for `move`/`save`/`control`). `MODEL_FEATURES`/`CATEGORICAL_FEATURES` in `cost_model.py` document, inline, the rationale behind each predictor choice — read those comments before adding/removing a feature. The A/B experiments backing each choice are runnable code: `analysis/cost/experiments/*.py` holds the ones that were adopted (each derives its "before" baseline from the current, already-adopted `MODEL_FEATURES`/`CATEGORICAL_FEATURES` rather than hardcoding a snapshot, so the comparison stays valid as those constants evolve); the rejected ones were deleted (git history only). Three fitting strategies share `feature_frame`: `fit_cost_model` (single OLS), `fit_segmented` (separate hero/troupe regressions), `fit_cost_model_factorial` (one OLS with categorical factors + `C(is_hero):...` interaction terms — only the first two are wired to `aospy cost fit`).

**Control is priced as its deviation from GW's tacit design rule** (`features.expected_control`, reconstructed with the user): a profile's *expected* control (light infantry 1, ≥5-HP infantry 2, hero 2, BEAST 1, MONSTER 5, ≥12-HP war machine 5, Ogor/Gargant monsters 10, banner heroes 5…) is **not** paid (p≈0.1); only `control_bonus` (epic models at 10-15, a few named "leader" characters, ≈+14 pts/point, p<0.001) and `control_deficit` (10-HP mounted/chariot heroes kept at 2, ≈−8 pts/point) enter `MODEL_FEATURES`. Raw `control` conflated control with unit type/model size (R² adj 0.8575 → 0.8600; banner heroes no longer look under-costed). Experiment: `analysis/cost/experiments/control_profile.py`. The rule partly keys on names (banners, Loonboss on Giant Cave Squig) and armies (Ogor Mawtribes, Sons of Behemat): extend it when a new battletome adds such profiles. For *ability* scoring control stays a weak stat regardless of its price (user's table-value rule).

Deliberately **not** ported: an ability-power axis (StatHammer's LLM-scored `ability_scores.py`) and a tactical-role ranking (`roles.py`) — aospy stores no per-unit ability text, only a free-text Crit tag per weapon. `wizard_level`/`priest_level` (from the `WIZARD (N)`/`PRIEST (N)` keywords) are the one exception, giving casters a direct — if narrow — ability-power proxy.

`CostModelResult.model` (the fitted `statsmodels` object, populated by both `fit_cost_model`/`fit_cost_model_factorial`) and `predict_one(result, features)` exist purely so `bonus_simulator/whatif.py` can predict a cost for an in-memory, not-yet-persisted `UnitFeatures` row (e.g. a unit with a bonus applied) by reusing patsy's formula-encoding rather than hand-rolling the categorical dummies. Neither is used by `aospy cost fit`/`cost residuals` or the PDF reports, which only read `coefficients`/`residuals`.
